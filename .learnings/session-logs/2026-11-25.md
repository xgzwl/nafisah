## 第二轮（UI 精修）· 新坑

- **headless 新版 Chrome 在 Windows 有最小视口（约 526px）。** `--window-size=390` 实际以 526px 布局，截图只保留左侧 390px，看起来像「手机端横向溢出」，极易误判为站点 bug。正确做法是 CDP `Emulation.setDeviceMetricsOverride`（width/mobile/deviceScaleFactor），本项目实测 390px 下 `scrollWidth == clientWidth`，站点无溢出。`--dump-dom` 的视口也与 `--screenshot` 不一致，不能拿它测布局。
- **CDP 整页截图有两个坑：**（1）视口只有 900 高时，`captureBeyondViewport` 不会触发 `loading="lazy"`，视口外的图片是空的——后来在探针页里移除 `loading="lazy"` 解决，不要在 CDP 里注入滚动循环，那个 Promise 会因页面高度动态增长而挂住；（2）页面超过约 1600 CSS px 时一次性栅格化会超时或爆内存，必须纵向分片截取再拼接。
- **`::first-letter` 会吞掉紧邻的撇号。** 文本 `I've` 的首字下沉实测把 `I'` 整体当作首字母并放大变色，配合 `padding-right` 使首词读成两个词。且字号放大 2.5 倍后字形右边距同比放大，光去掉 padding 还不够，需要负 margin 补偿。
- **`:last-child` 规则的特异性会穿透媒体查询。** 为修两列空洞写了 `.gallery-item:last-child img { aspect-ratio: 4/5 }` 放在 `max-width:900px` 里，它特异性高于 `max-width:767px` 里的 `.gallery-item img { aspect-ratio: auto }`，导致手机端末图被裁成 4:5。断点覆盖类改动必须限定区间（`min-width:768px and max-width:900px`）而不是只写上界。
- **灰度直方图比「看起来暗」可靠。** 判断一张图是否可用，看中位值/P90 比看缩略图靠谱：本次主图中位 1.0、P90 3.9、仅 1.8% 像素 > 30，结论是「没有图像数据」而非「氛围暗」。

### 决策

- 原先为守「仅 PD/CC0」把 CC BY 素材全部排除，导致可选范围过窄。owner 确认「简单的署名可以」，遂把许可放宽为 **PD / CC0 / CC BY**，以「图注下方一行小字署名」落地，不引入第三方外链（站点硬约束）。
- 只替换 1 张、不重排全站：`banner-old-library.webp` 是唯一暖偏 +0.0 的纯黑白图（亮度 138.5），靠 CSS sepia 勉强染色，与整站色系最不协调。

### 新坑

- **Commons 的 categorymembers 混入大量非主题文件。** `Category:Biblioteca Joanina` 取回的前三张分别是「墙面壁龛角落」「建筑外立面+橘树苗圃」「教堂外立面台阶」，靠分类名判断素材类型会白跑。必须缩略图目检。

### 数字口径（分歧根源，务必统一）

- **`getBoundingClientRect().width` 用小数，`clientWidth` 按 CSSOM 规约返回整数**，定稿一律用 `rect.width`。两者的 **+0.41px 偏差只在 ≤560px 存在，且以 root=16px 为前提**：该断点 `.shell` 是 `min(100% - 1.4rem, 1120px)`，`1.4rem × 16 = 22.4px` 不是整数，宽度小数部分恒为 .6，经 Chrome 的 1/64px LayoutUnit 对齐成 .59375，`clientWidth` 向上取整成 .59+0.41；**>560px 时** `.shell` 换成 `min(1120px, 100% - 2.5rem)`，`2.5rem = 40px` 为整数，两个 API 返回完全相等，所以拿 `clientWidth` 复验 820/1440 会看到 delta=0——那是正常的，不是测法变了。站内没有 `html { font-size }` 覆写（只有 `scroll-behavior`），取浏览器默认 16px；**用户若改根字号，1.4rem 的奇偶性会变**（如 root=20px → 28px 为整数），该偏移随之消失。
- **flex item / gap 计数**：细线可见 = 5 item / 4 gap；`≤359` 细线 `display:none` 后伪元素不生成 = 3 item / 2 gap。按固定 4 gap 算会高估 12.8px。
- **Cinzel 整串 advance 常数**（不要用「0.6x em × 字数」）：`NAFISAH RIDDLE` = 8.450em、`TOM RIDDLE` = 6.405em。两串均值差 6%，统一系数会把差异抵消掉。
- **Georgia 回退只宽 +2.1%**（实测 0.6225 → 0.635em），不是「0.70em、宽 11%」。后者是只比字宽、漏了文字只占内容 83% 的复合假象。

|---|---|---|
| 320 | 34.19 / 33.38 | 15.42 / **11.52** ← 全场最小 |

### 回归红线（改任一项必须重验，四条同等效力）

1. **改 `≤359` 的细线 `display:none`** → 重验 320 顶部。判定必须用**容器高度法**，不能用「`rect.top` 去重」——心形有 `translateY(-0.045em)`，亚像素会让单行被判成多行。旧版无此规则时 320px 内容 324.42 vs 可用 297.59，被压成孤儿细线占整行。
2. **任何地方出现 `font-weight ≥ 500`** → 重验 320 底部。现有 400/600 是同一份字形（MD5 相同），假 600 渲染即 400；一旦换成真加粗，姓名宽度 +4%，320 底部余量从 11.52 掉到约 1.7px，**而且不会报任何错**。
3. **改 `padding-inline` 或姓名字号下限** → 重验 320/360 底部。注意下限是 **`0.875rem` 这个相对值，不是绝对的 14px**：root=16px 时它等于 14px，root=13px 时是 11.375px，随用户根字号等比缩放属预期行为。把「不得低于 14px」写进验收条件，任何人在非 16px 根字号下复验都会误判失败（实测 root=13px/320px 下姓名为 11.375px，横溢仍为 0）。
4. **不得为「稳住 11.52 这个数」给 `html` 加 `font-size` 覆写。** 锁 root 等于把用户的字号偏好一刀切掉——拿真实的无障碍损失换账面余量，方向反了。站内不锁 root 是正确做法，应作为前提被保护，不能当漏洞修补。

### 已知偏差（不修，如实记录）

1. `≤359` 的 `.devotion-heart { font-size: .9em }` **只作用于顶部**，底部仍被 `.devotion--seal .devotion-heart(.94em)` 以更高特异性覆盖，实测 12.59 vs 13.16，差 0.56px。不回改代码——为 0.56px 再加一条更高特异性规则，是把文档问题换成两个代码分支。已在 CSS 行尾就地注释。
2. 320px 底部 Georgia 回退态余 11.52px，全场最紧，不处理。

### 用户放大字号（root ≠ 16px）不是缺陷

root=20px 时 `1.4rem = 28px` 变整数，前述 +0.41 偏移自行消失；同时姓名字号随 rem 放大约 25%、`seal` 内容盒因容器收窄而变小，`flex-wrap` 必然触发换行 → **两行、内容完整、无横向滚动**。

这不是「余量被偷偷吃成临界」，是整体等比放大后超出容器一个身位。**符合 WCAG 1.4.4（文本放大至 200% 不丢失内容或功能）**，且是实测而非推断：注入 root = 13 / 16 / 20 / 32px 四档 × 320px 视口，`document.documentElement.scrollWidth` 恒等于 `clientWidth`（横向溢出 0），root=32px（即 200%）时题献框折成 2.3 行、内容完整、无横向滚动。

所以 root 变化不处理，理由不是「超出范围」，而是「本来就合规」。把这条写成「缺陷」会诱导后人去锁 root——那才是真的破坏无障碍。

### 本轮的过程教训（比技术细节更贵）

- **把最终 CSS 拆成六条增量消息发给执行者，等于让他自己拼规格。** 结构/语义/i18n/无障碍全部落地正确，唯独媒体查询收口反复出错——不是执行者不细心，是规格分发方式的问题。应一次给不可分割的完整块。
- **转述第三方算出的数值前必须自己代一遍。** 我把视觉的 4.8px 直接转给执行者并加了「临界档」定性，实际按终值表是 18.03px，害得对方按错误红线调整。
- **别人给的余量数值，要么自己复现，要么在决策里标注「按转述待验」。** 我手里有 CDP 测量脚本却没跑，凭一句「1.5px 临界」下了调参指令，随后被迫撤回。
- **测量错误有三种，性质不同**：工具缺陷（伪元素未计）、表述问题（分母用了 shrink-to-fit 的自身宽度，得出假负数）、API 语义误解（整数取整）。三者都表现为「数值差一点」，但纠正方式完全不同——所以报数值时必须同时给「内容宽、可用宽、各自怎么量的」。
- **几何判据要连判定算法一起写进验收条件。** 「是否单行」留下歧义让两边各自实现，结果一边用 `rect.top` 去重被判成 3 行（心形 `translateY` 亚像素）、一边用行高容差得单行。正解是 `Math.abs(rect1.top - rect2.top) < 2`。
- **不要给估算值设验收阈值。** `header ≤180/240px` 是早期估的，实测 HEAD 基线（无题献带）就有 201.6px，拿它当条件等于要求改既有导航。改为可归因的三条：题献带贡献 ≤40px + 不改变 nav 行数 + 不与 main 重叠。
