## 第二轮（UI 精修）· 新坑

- **headless 新版 Chrome 在 Windows 有最小视口（约 526px）。** `--window-size=390` 实际以 526px 布局，截图只保留左侧 390px，看起来像「手机端横向溢出」，极易误判为站点 bug。正确做法是 CDP `Emulation.setDeviceMetricsOverride`（width/mobile/deviceScaleFactor），本项目实测 390px 下 `scrollWidth == clientWidth`，站点无溢出。`--dump-dom` 的视口也与 `--screenshot` 不一致，不能拿它测布局。
- **CDP 整页截图有两个坑：**（1）视口只有 900 高时，`captureBeyondViewport` 不会触发 `loading="lazy"`，视口外的图片是空的——后来在探针页里移除 `loading="lazy"` 解决，不要在 CDP 里注入滚动循环，那个 Promise 会因页面高度动态增长而挂住；（2）页面超过约 1600 CSS px 时一次性栅格化会超时或爆内存，必须纵向分片截取再拼接。
- **`::first-letter` 会吞掉紧邻的撇号。** 文本 `I've` 的首字下沉实测把 `I'` 整体当作首字母并放大变色，配合 `padding-right` 使首词读成两个词。且字号放大 2.5 倍后字形右边距同比放大，光去掉 padding 还不够，需要负 margin 补偿。
- **`:last-child` 规则的特异性会穿透媒体查询。** 为修两列空洞写了 `.gallery-item:last-child img { aspect-ratio: 4/5 }` 放在 `max-width:900px` 里，它特异性高于 `max-width:767px` 里的 `.gallery-item img { aspect-ratio: auto }`，导致手机端末图被裁成 4:5。断点覆盖类改动必须限定区间（`min-width:768px and max-width:900px`）而不是只写上界。
- **灰度直方图比「看起来暗」可靠。** 判断一张图是否可用，看中位值/P90 比看缩略图靠谱：本次主图中位 1.0、P90 3.9、仅 1.8% 像素 > 30，结论是「没有图像数据」而非「氛围暗」。
